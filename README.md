# LearningLanguages 生成パイプライン

このリポジトリは、`languages-curriculum.md` を最上流ソースとして、指定した 1 つのプログラミング言語に専用化した学習仕様、Learning MISRA 仕様、ハンズオン学習ドキュメント、実行可能なサンプルコード、CI/CD ワークフローを生成するためのものです。

生成物は、初心者が説明を読むだけで終わらず、コードを最初から段階的に実装し、各段階で動作を確認しながら、CLI ツール、デスクトップ GUI アプリ、サーバ / Web API、データ処理パイプラインなどのビジネスアプリケーションを自力で作成・拡張できるようになることを目的とします。

要求仕様の単一ソースは `languages-curriculum.md` です。本 README は、その要求を実行するための操作手順と要約を示します。両ファイルに不一致が見つかった場合は生成を開始せず、`languages-curriculum.md` を基準に本 README を同期してから再開します。

## 対象プラットフォーム

学習ドキュメント、サンプルプロジェクト、検証手順の対象配分は、次のとおりです。割合はプラットフォーム固有の説明、実装、トラブルシューティング、実行確認に割り当てる重点度を示し、言語共通の説明を無理に行数比で分割するものではありません。

- Windows x86_64: **70%**
- Linux x86_64: **10%**（正式対象は Ubuntu 24.04 LTS。WSL2 の Debian は開発環境として継続使用）
- Raspberry Pi 4 以降の ARM64: **20%**（Raspberry Pi OS 64-bit および Ubuntu 24.04 LTS 64-bit）

Raspberry Pi は GPIO、I²C、SPI、UART、PWM などを扱う組み込み機器教材ではなく、ARM64 Linux 上で汎用アプリケーションをビルド、実行、テスト、配布する対象として扱います。Windows 上の MobaXterm から SSH で接続し、教材で作成した単体 GUI アプリケーションは X11 フォワーディングで目視確認します。Raspberry Pi のデスクトップ全体の遠隔操作は対象外です。

正式ターゲットは、Windows x86_64、Ubuntu 24.04 LTS x86_64、Raspberry Pi OS 64-bit ARM64、Ubuntu 24.04 LTS ARM64 の 4 実行環境です。実行可能な項目は、プラットフォーム固有であることが学習目標の項目を除き、原則として 4 環境すべてでビルド・テスト・実行できることを完成条件とします。技術的に対応できない環境がある場合は黙って対象外にせず、理由、代替案、影響範囲を提示してユーザ確認を得たうえで、選択言語用の `<出力ディレクトリ>/master-spec.md` に例外を記録します。

GitHub Actions では、Raspberry Pi 4 以降の実機をセルフホステッドランナーとして使うネイティブビルド・テストを基本とし、CI での ARM64 クロスビルドも併記します。実機は 1 台とし、Raspberry Pi OS と Ubuntu 24.04 LTS を切り替えて順番に検証するため、両 OS の同時実行を前提にしません。2 OS の結果は、同じコミット、選択言語と Task のバージョン、依存ロック、テストデータ、合格基準に対して取得します。OS 固有の sysroot、libc、システムパッケージは無理に同一化せず、差分を記録して成果物を区別します。クロスビルド成果物は GitHub Actions のアーティファクトとして保存し、対象 OS で起動したセルフホステッドランナーが取得して実機テストします。GitHub ホステッドランナーから Raspberry Pi への外部向け SSH 接続は必須にしません。クロスビルドの成功だけで Raspberry Pi 対応済みとはせず、成果物を実機へ配置して起動・テストするところまで確認します。GUI は CI の仮想ディスプレイ上で自動テストし、MobaXterm の X11 フォワーディングで実画面を補完確認します。

macOS arm64 は上記の配分外の補助サポートとし、CI ビルドと Mac 所有者向けのデバッグ手順を維持します。具体的なツール、バージョン、ターゲットトリプル、ランナーラベル、クロスコンパイル方法は、選択言語用の `<出力ディレクトリ>/master-spec.md` で確定します。

## タスクランナー

コードの Formatter、Lint、ビルド、テスト、実行、パッケージ化、リリース、クリーン、CI 用検証には、Taskfile.dev の **Task**（`go-task`）を標準タスクランナーとして使用します。教材で生成する実行可能プロジェクトには `Taskfile.yml` を配置し、学習者と CI の正準コマンドを `task fmt`、`task lint`、`task build`、`task test`、`task run`、`task package`、`task release`、`task clean`、`task ci` に統一します。項目に存在しない処理は省略できますが、同じ意味の別名を無秩序に追加しません。言語固有のコンパイラ、パッケージマネージャ、テストランナーは `Taskfile.yml` から呼び出し、学習ドキュメントでは Task タスクと内部で実行される言語固有コマンドの対応を説明します。サーバや GUI などの `task run` は、起動確認、ヘルスチェック、制限時間、正常終了までを再現できる検証モードを持たせます。`task release` の通常検証はローカルのリリース候補作成または dry-run に限定し、レジストリ公開、タグ作成、外部リリース更新は保護されたリリースワークフローで明示承認された場合だけ実行します。`task clean` は project 内の再生成可能な成果物だけを対象とし、ソース、設定、依存ロック、テストデータを削除しません。

教材で作成するビルド自動化には `make` / `Makefile` / GNU Make を使用・生成せず、ビルド、テスト、リリースの学習者向け入口を Task に一本化します。外部依存自身の内部ビルドが Make を使用する場合は教材のタスクランナーとは区別し、回避不能な理由、影響、代替案を提示してユーザ確認を得たうえで、選択言語用の `<出力ディレクトリ>/master-spec.md` に例外を記録します。

第 1 章の環境構築には、Windows x86_64、WSL2 Debian、Ubuntu 24.04 LTS x86_64、Raspberry Pi OS 64-bit ARM64、Ubuntu 24.04 LTS ARM64、および補助対象の macOS arm64 ごとに Task のインストール、更新、`PATH` 反映、`task --version` による確認、アンインストールまたは復旧手順を記載します。Windows の第一選択は WinGet の `Task.Task`、Ubuntu / Debian 系は Task 公式 APT リポジトリ、macOS は公式 Homebrew tap とし、選択バージョンと代替導入方法は `<出力ディレクトリ>/master-spec.md` で確定します。

Windows は日本語表示環境でも動作することを必須とします。`Taskfile.yml` と学習者管理下のテキストファイルは原則 UTF-8 とし、日本語と空白を含む作業パス・ファイル名・標準入出力・ログ・アーカイブ名で `task build`、`task test`、該当する場合は `task package` / `task release` を検証します。パスを引用せずに連結する処理、ユーザ名やドライブ文字の固定、CP932 固有の暗黙変換、Windows に標準搭載されない Unix コマンドへの依存を禁止します。改行、BOM、コンソール、サブプロセスの具体的な文字コード方針は、選択言語用の `<出力ディレクトリ>/master-spec.md` で確定します。

生成パイプラインは次の順序で進めます。

```text
README.md（操作手順） + languages-curriculum.md（要求仕様）
  -> 初回または上流契約変更時に prompts/pipeline/ の 9 プロンプトを生成・監査
  -> target_language を 1 言語確認
  -> <出力ディレクトリ>/output-spec.md
  -> <出力ディレクトリ>/master-spec.md
  -> <出力ディレクトリ>/misra-spec.md
  -> <出力ディレクトリ>/spec.md
     + prompts/generation/<target_language>/generate-item.md
  -> CLAUDE.md / AGENTS.md
  -> 項目単位の学習ドキュメント（内容確認用）
     + サンプルコード / サンプルプロジェクト / CI/CD ワークフロー
  -> ユーザによる内容承認
  -> 91-verify.md による必須検証
  -> 必要に応じて 90-audit.md による監査
  -> 合格なら項目完了、不合格なら同じ項目を再生成
```

`output-spec.md`、`master-spec.md`、`misra-spec.md`、`spec.md` は共通ファイルとしてリポジトリ直下に作成しません。すべて選択言語の出力ディレクトリ内に作成し、1 ファイルに複数言語の決定や例を混在させません。共通仕様雛形と共通の Learning MISRA 成果物も作成しません。

## プロンプト配置

プロンプトは用途別にディレクトリを分けます。

- `prompts/pipeline/`: 1 言語パイプラインを開始する前の制御・仕様派生・検証用プロンプト
- `prompts/generation/<target_language>/`: 選択言語専用の項目生成プロンプト

`prompts/pipeline/` のプロンプト自体は複数言語から共通利用しますが、1 回の実行では必ず `target_language` を 1 言語に固定します。上流の `README.md` と `languages-curriculum.md` は共通入力として参照し、言語別仕様・docs・projects は選択言語の出力ディレクトリだけへ生成します。定義済みの生成用プロンプトとリポジトリ直下のエージェントコンテキストを除き、別言語の出力ディレクトリを読み書きしません。

`README.md` は操作説明と、各プロンプトファイルを起動するためのコピー用入力文を管理します。作業ロジックを持つ実行プロンプト本体は `prompts/` 配下のファイルとして管理し、README の入力文へ重複実装しません。

## ブートストラップ／契約同期

初期状態で `prompts/pipeline/` が存在しない場合、9 ファイルのいずれかが欠落・不整合の場合、または上流契約を変更した場合は、通常パイプラインを開始する前に、AI コードエージェントへ `README.md` と `languages-curriculum.md` を入力し、本 README の手順と `languages-curriculum.md` の「パイプラインプロンプトのブートストラップ／契約同期契約」に従って次の 9 ファイルだけを生成または監査・更新させます。

- `prompts/pipeline/00-common-control.md`
- `prompts/pipeline/01-derive-output-spec.md`
- `prompts/pipeline/02-derive-master-spec.md`
- `prompts/pipeline/03-derive-misra-spec.md`
- `prompts/pipeline/04-run-language-pipeline.md`
- `prompts/pipeline/05-generate-agent-context.md`
- `prompts/pipeline/80-enable-language.md`
- `prompts/pipeline/90-audit.md`
- `prompts/pipeline/91-verify.md`

ブートストラップでは、言語別仕様、学習ドキュメント、サンプルプロジェクト、`CLAUDE.md`、`AGENTS.md` を生成しません。上記 9 ファイルがすでに存在する場合は、欠落・名称・責務・入出力契約を監査し、上流ルールが変わったファイルだけを更新します。ブートストラップ完了後に、次の通常実行へ進みます。

## AI コードエージェントへ実際に入力するプロンプト

`languages-curriculum.mdを実行して` とは入力しません。`languages-curriculum.md` は実行手順そのものではなく要求仕様であるため、この入力だけでは、AI が要約、レビュー、仕様生成のどれを行うべきか判断できません。

AI コードエージェントをリポジトリルートで起動し、以下のコードブロックを**1 回につき 1 つだけ**入力してください。`<target_language>` は `rust` や `go` など対象言語表の値へ、`<item_id>` は生成済みの `<出力ディレクトリ>/output-spec.md` にある項目 ID へ置き換えます。山括弧を残したまま入力してはいけません。

同じ会話で順番に実行することを推奨します。新しい会話で再開する場合も、対象言語と項目 ID を入力文へ必ず含めます。ただし、会話履歴だけを前提にしてはいけません。各プロンプトは実行開始時に対象言語の状態、出力先、必須入力ファイル、既存出力を再確認し、既存出力がある場合は上流変更と矛盾しないユーザ確認済み内容を保持して、必要な差分だけを適用します。既存ファイルの存在だけを承認済み・検証済みの根拠にはしません。AI から質問された場合は、その質問だけに回答し、対象プロンプトの完了報告を受けるまで次のプロンプトを入力しません。

### 0. パイプラインプロンプトを初回生成・契約同期する場合

`prompts/pipeline/` が存在しない場合、9 ファイルのいずれかが欠落・不整合の場合、または上流契約の変更を反映する場合に入力します。

```text

`README.md` と `languages-curriculum.md` を全文読み、`languages-curriculum.md` を単独で実行しようとせず、両ファイルに定義された「パイプラインプロンプトのブートストラップ／契約同期契約」を実行してください。

これは内容の要約やレビューの依頼ではありません。次の 9 ファイルだけを生成または必要なものだけ更新してください。
- prompts/pipeline/00-common-control.md
- prompts/pipeline/01-derive-output-spec.md
- prompts/pipeline/02-derive-master-spec.md
- prompts/pipeline/03-derive-misra-spec.md
- prompts/pipeline/04-run-language-pipeline.md
- prompts/pipeline/05-generate-agent-context.md
- prompts/pipeline/80-enable-language.md
- prompts/pipeline/90-audit.md
- prompts/pipeline/91-verify.md

9 ファイルそれぞれに `## 実行方法` を設け、README の対応する入力文と同じ必須パラメータ、処理範囲、禁止事項、停止条件を記載してください。言語別仕様、generate-item.md、学習ドキュメント、projects、CLAUDE.md、AGENTS.md はまだ生成しないでください。未決定事項があれば日本語で 1 件ずつ質問してください。9 ファイルの生成・更新と自己検査が完了したら、変更したファイル、変更しなかったファイル、次に入力する `00-common-control.md` の呼び出し文を報告して停止してください。
```


## 実行順

AI コードエージェントをリポジトリルートで起動し、§「AI コードエージェントへ実際に入力するプロンプト」の対応コードブロックを、次の順に 1 つずつ入力してください。対象言語表で状態が `対応中` の言語を生成する通常実行を示します。

1. `prompts/pipeline/00-common-control.md` を入力し、`target_language` を 1 言語確認する。状態が `対応中` なら手順 2 へ進み、それ以外なら通常実行を停止して §「未対応言語の対応中化手順」へ進む
2. `prompts/pipeline/01-derive-output-spec.md` で `<出力ディレクトリ>/output-spec.md` を作成する
3. `prompts/pipeline/02-derive-master-spec.md` で `<出力ディレクトリ>/master-spec.md` を作成する
4. `prompts/pipeline/03-derive-misra-spec.md` で `<出力ディレクトリ>/misra-spec.md` を作成する
5. `prompts/pipeline/04-run-language-pipeline.md` で `<出力ディレクトリ>/spec.md` と `prompts/generation/<target_language>/generate-item.md` を作成する
6. `prompts/pipeline/05-generate-agent-context.md` でリポジトリ直下の `CLAUDE.md` と `AGENTS.md` を作成する
7. `prompts/generation/<target_language>/generate-item.md` を、1 項目について入力する
8. ユーザが生成された学習ドキュメントとプロジェクトを確認し、内容を承認するか修正を指示する。この承認だけでは項目完了にしない
9. 承認後、`prompts/pipeline/91-verify.md` を同じ項目 ID に対して実行し、最終プロジェクトだけでなく、学習ドキュメントの手順を空の検証用作業場所から順番に再現できることを確認する
10. 必要に応じて `prompts/pipeline/90-audit.md` を同じ項目 ID に対して実行する

手順 7〜10 は、`<出力ディレクトリ>/output-spec.md` と `<出力ディレクトリ>/spec.md` に定義された各項目について繰り返します。ユーザ未承認、`91-verify.md` 不合格、または `90-audit.md` の未解決指摘がある場合は、次項目へ進まず同じ項目を `generate-item.md` で再生成します。

`output-spec.md` には、全項目の ID、docs/projects パス、前提項目、生成順、対象プラットフォーム、検証方式、`Taskfile.yml` と必須タスク、Windows 日本語環境の検証方式、DoD、最終状態ファイル台帳の形式、章別・種別の正確な件数を持つ生成対象台帳を作成します。最終状態ファイル台帳では、全文掲載するテキスト、リポジトリ管理するバイナリ学習資産、再生成する成果物、外部依存、秘密情報を区別します。`output-spec.md` 自体には実行時の合否や進捗を書き込まず、検証結果は `91-verify.md` の実行結果として報告します。アルゴリズムのカテゴリ名や未確定項目が残る場合、第 11 章の UI レイアウト 12 件・基本コントロール 21 件の具体名が確定していない場合、第 8 / 10 / 11 章の全 34 アプリが揃わない場合、または第 12 章の Raspberry Pi CI/CD 追加 4 項目が揃わない場合は、`spec.md` と `generate-item.md` の生成へ進みません。

言語非依存の共通仕様雛形を生成する段階は設けません。言語別 `spec.md` は、`languages-curriculum.md` と選択言語用の `output-spec.md`、`master-spec.md`、`misra-spec.md` から直接派生します。`misra-spec.md` は、`master-spec.md` で確定したツールチェーン、Linter、Formatter、静的解析ツールを参照して検出方法を具体化し、同じ設定を重複決定しません。

`CLAUDE.md` と `AGENTS.md` はリポジトリ直下に置きます。両ファイルは `README.md` と `languages-curriculum.md` の横断ルールから生成し、特定言語の設定や進捗を固定しません。実行時の `target_language` と言語別仕様ファイルのパスは `generate-item.md` から受け取ります。別言語のパイプラインを実行しただけでは両ファイルに差分を発生させません。

生成用プロンプトの出力先は次の形式です。

```text
prompts/generation/<target_language>/generate-item.md
```

例:

```text
prompts/generation/rust/generate-item.md
```

## 生成される学習ドキュメントの必須方針

すべてのハンズオン学習項目は、完成コードを先に提示するだけの説明ではなく、学習者が空の作業ディレクトリまたは直前段階から実装を積み上げる形式にします。各実装ステップには、目的、開始状態、作業ディレクトリ、対象 OS / シェル、操作、変更するファイルの編集後の完全な内容、コードの説明、必要な動作図、Task を入口とする動作確認、期待結果、確認ポイント、失敗例を含めます。

対応する `<出力ディレクトリ>/projects/...` の正準プロジェクトには、ドキュメントの最初のコードや途中ステップの状態ではなく、**全ステップを完了した最終状態**を出力します。ソース、設定、依存ロック、`Taskfile.yml`、テスト、テストデータ、ワークフローなど、ドキュメント末尾の「まとめ: 動作する完全コード」に列挙された学習者管理下の全ファイルを一致させます。テキストとして再掲できない画像などのバイナリ学習資産は、パス、役割、取得または作成手順、SHA-256 を台帳に記録します。スターターコード、最小起動状態、未実装部分、後続ステップ待ちのコードを正準プロジェクトのルートへ出力してはいけません。

生成時は、最初のコードブロックを project へコピーする方式を禁止します。全実装ステップを反映した単一の最終状態から、ドキュメント末尾の完全コードと正準 project の両方を生成します。`91-verify.md` では、ドキュメントを空の検証用作業場所から最後まで再現した結果、末尾の完全コード、対応 project の 3 者について、対象ファイルのパス・内容・実行結果が一致することを確認します。テキストは言語別文字コード方針を適用して比較し、リポジトリ管理するバイナリ学習資産は生バイトの SHA-256 で照合します。不一致、余分な初期コード、最終機能・テスト・Task タスクの欠落が 1 件でもあれば不合格とします。

動作の流れ、データフロー、呼び出し順序、状態遷移、非同期処理、エラー経路など、動作理解に関わる説明には Mermaid で描画した図を必須とします。ただし、読者に見せる図の見出しやキャプションを「Mermaid」「Mermaid 図」「フローチャート」「シーケンス図」「図 1」だけで済ませてはいけません。「認証要求がデータベースへ保存されるまで」のように、図が表す処理や関係を具体的に示すタイトルを付けます。

各図の直前には「図の概要」として、図の目的、開始点と終了点、主要な登場要素、注目すべき流れを初心者向けに説明します。図の直後には「図の読み方」と、図中のノード・矢印・状態が実際のファイル、関数、型、ジョブのどこに対応するかを文章または表で説明します。Mermaid は描画形式としてのみ扱い、図の内容説明の代わりにしません。

アルゴリズム章は、各アルゴリズムまたはデータ構造を独立した学習項目にします。アルゴリズム自体の考え方、適用場面、図解、疑似コード、手計算トレース、変数遷移、計算量、実装コードとの対応、段階実装、テストを揃え、言語とアルゴリズムを同時に学べる内容にします。

サンプルアプリケーションは、第 8 章の 4 件、第 10 章の 12 件、第 11 章の 18 件（簡易タスク管理を 3 フレームワークで実装する 3 件を含む）の合計 34 件をすべて個別に生成します。各アプリは生成前に全機能、利用者の操作または入力、期待結果、受入条件、必要なテストを機能台帳へ確定します。ドキュメントでは要件・画面または入出力・データ・処理・コード・テストの対応を説明し、機能ごとに段階実装します。完成後には、学習者が機能追加や置き換えを行う拡張演習も含めます。

## 未対応言語の対応中化手順

対象言語表で状態が `対応中` 以外の言語を生成する場合は、通常実行の前に `prompts/pipeline/80-enable-language.md` を実行します。

1. `prompts/pipeline/00-common-control.md` を入力し、`target_language` を 1 言語確認する
2. 対象が `将来予定` または `要追加定義` なら、`prompts/pipeline/80-enable-language.md` を実行する
3. AI が不足している言語固有要求と決定候補を依存関係順に提示し、ユーザに 1 件ずつ確認する
4. 確定内容を `languages-curriculum.md` に反映し、未確定マーカーがないことを確認して対象言語を `対応中` にする
5. §「実行順」の手順 1 から通常実行を開始する

`80-enable-language.md` は、共通仕様ファイルや共通 MISRA ルールセットを作成しません。言語の対応中化に必要な最上流要求だけを `languages-curriculum.md` に反映します。対象言語用の `output-spec.md`、`master-spec.md`、`misra-spec.md` は通常実行で作成します。

## 未決定事項の扱い

AI コードエージェントは、ライブラリ、パッケージ、バージョン、API、OS 要件、テスト方針などの未決定事項を推測で確定してはいけません。

未決定事項がある場合は、候補一覧、推奨候補、推奨理由、影響範囲を提示し、ユーザに 1 件ずつ確認します。ユーザの回答を得てから次の質問へ進みます。

## 対応言語

対象 `target_language` の一覧、出力ディレクトリ、状態（`対応中` / `将来予定` / `要追加定義`）は、`languages-curriculum.md` §「対象言語の指定」の対象言語表を単一ソースとして参照します。本 README は重複した状態リストを保持しません。

## 出力先

主な出力先は次の通りです。

- 言語別出力仕様: `<出力ディレクトリ>/output-spec.md`
- 言語別決定事項: `<出力ディレクトリ>/master-spec.md`
- 言語別 Learning MISRA 仕様: `<出力ディレクトリ>/misra-spec.md`
- 言語別詳細仕様: `<出力ディレクトリ>/spec.md`
- 大規模生成用コンテキスト: リポジトリ直下の `CLAUDE.md` / `AGENTS.md`
- 学習ドキュメント: `<出力ディレクトリ>/docs/`
- サンプルコード / サンプルプロジェクト / CI/CD ワークフロー: `<出力ディレクトリ>/projects/`

`docs/` と `projects/` の内部構造は、選択言語用の `<出力ディレクトリ>/output-spec.md` を単一ソースとします。各章ディレクトリのトップとなる索引ドキュメントは `README.md` とし、`index.md` は生成しません。

`prompts/pipeline/` と `prompts/generation/` はプロンプト管理用であり、最終学習成果物の出力先ではありません。
